Go 1.18 引入泛型时，社区分成两派：一派认为终于能删掉一半的 `interface{}`，另一派担心语言复杂度失控。
两年过去，我们的代码库给出了一个不好看但诚实的答案：**泛型在容器和工具函数上收益巨大，在业务逻辑上几乎没有。**

## 统计口径

样本是主仓库，40 万行 Go（不含测试和生成的代码），统计截止 2026 年 5 月：

| 指标 | 数值 |
| --- | --- |
| 泛型函数 / 类型 | 214 个 |
| 涉及文件 | 96 个 |
| 使用 `interface{}` / `any` 的位置 | 1,842 个 → 1,203 个（−35%） |
| 因泛型删除的重复代码 | 约 9,100 行 |
| 因泛型新增的抽象层 | 约 1,400 行 |

净减少约 7,700 行。但**减少集中在 12 个文件里**，其中 6 个是集合与缓存工具。

## 真正赚到的地方

### 1. 类型安全的容器

这是最没有争议的收益。以前每个业务类型都要写一份 `FooCache`，现在一份就够：

```go
// 改造前：每个类型一份，逻辑完全一样，只有类型不同。
type UserCache struct {
    mu    sync.RWMutex
    items map[string]*User
}
func (c *UserCache) Get(k string) (*User, bool) { /* … */ }

// 改造后：一份实现，编译期类型检查，没有反射开销。
type Cache[K comparable, V any] struct {
    mu    sync.RWMutex
    items map[K]V
}

func (c *Cache[K, V]) Get(key K) (V, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.items[key]
    return v, ok
}

func (c *Cache[K, V]) GetOrLoad(key K, load func(K) (V, error)) (V, error) {
    if v, ok := c.Get(key); ok {
        return v, nil
    }
    v, err := load(key)
    if err != nil {
        var zero V
        return zero, err
    }
    c.mu.Lock()
    defer c.mu.Unlock()
    c.items[key] = v
    return v, nil
}
```

`var zero V` 这个惯用法值得记住：泛型里没有 `nil` 的概念（`V` 可能是 `int`），
返回零值只能这么写。

### 2. 切片操作

`Map`、`Filter`、`Reduce` 这类函数在 40 万行的代码库里总共被调用 3,100 多次，
替换掉的手写循环大约 4,200 行。

```go
func Map[T, U any](in []T, f func(T) U) []U {
    out := make([]U, 0, len(in))
    for _, v := range in {
        out = append(out, f(v))
    }
    return out
}

func Filter[T any](in []T, keep func(T) bool) []T {
    out := in[:0:0] // 新底层数组：不覆盖入参，也不额外分配容量
    for _, v := range in {
        if keep(v) {
            out = append(out, v)
        }
    }
    return out
}
```

`in[:0:0]` 是这里唯一的技巧。写成 `in[:0]` 会复用入参的底层数组，
调用方如果还持有原切片，就会看到被覆盖的数据。这个 bug 我们在 code review 里抓到过两次。

{{< callout type="warn" title="别在热路径里无脑用 Map" >}}
`Map` 每次都会分配一个新的底层数组。在我们的序列化热路径上，把它换成预分配的循环，
GC 压力下降了 11%。**工具函数好用，但它隐藏了一次分配**——这是它唯一的代价。
{{< /callout >}}

## 收益可疑的地方

### 把 interface{} 换成 any 不等于泛型

我们最初有 300 多处改动只是把 `interface{}` 写成了 `any`。这是纯粹的语法糖，
`go vet` 一行命令就能做，而且不带来任何类型安全。

真正的泛型改造应该满足一个标准：**调用点不再需要类型断言**。
如果一个函数体内部还在做 `v.(T)` 或者用反射，那这次改造没有意义。

### 业务逻辑里的泛型抽象层

我们曾经尝试把「各种审批流」抽象成一个泛型状态机：

```go
// 这个抽象最后被删掉了。
type Workflow[S State, E Event, C any] interface {
    Apply(ctx context.Context, s S, e E, cfg C) (S, error)
    Validate(s S) error
}
```

三个业务流各自只有 8 到 12 个状态，写三遍加起来 600 行，抽象之后核心 400 行加三个适配器 350 行。
**行数没减少，可读性下降了**，新人要理解一个业务流必须先读懂泛型框架。半年后我们把它拆回了三份。

教训：泛型适合「逻辑相同、类型不同」，不适合「形态相似、语义不同」。

## 编译时间

这是最容易被忽略的成本。全量构建时间：

| 版本 | 全量构建 | 增量构建（改一个包） |
| --- | --- | --- |
| 改造前（Go 1.21） | 42.1 s | 3.4 s |
| 改造后（Go 1.23） | 51.7 s | 4.9 s |
| 对照：同时期 Go 版本升级本身 | +3.2 s | +0.4 s |

扣掉版本升级的影响，泛型让全量构建慢了约 **6 秒（+15%）**，增量构建慢了约 **1.1 秒**。
原因是编译器要为每个实例化组合生成代码。我们把 `Cache` 的实例化组合从 40 种收敛到 9 种之后，
多出来的时间降到了约 2.5 秒。

{{< callout type="tip" title="控制实例化数量" >}}
泛型代码的编译成本大致正比于**实例化组合数**，不是泛型函数个数。
如果某个泛型函数被 30 种类型组合实例化，考虑把它改成非泛型 + 一次类型断言，
或者把类型参数收敛到少数几个接口上。
{{< /callout >}}

## 我们的使用准则

现在的内部规范只有四条：

1. **容器和算法工具**：默认用泛型。
2. **有超过 3 个类型需要同一套逻辑**：用泛型。
3. **只有一个类型在用**：不要泛型，直接用具体类型。
4. **逻辑里出现反射或类型断言**：说明抽象错了，退回去。

第 3 条最关键。我们删掉的泛型代码里，超过一半是「只有一个调用点」的提前抽象。

## 小结

两年下来，泛型在我们代码库里的净收益是约 7,700 行和一批真实的类型安全。
但它的分布极不均匀：**6 个工具文件贡献了 80% 的收益**。

如果你的代码库还没有大规模用泛型，我的建议是从容器开始，不要从业务抽象开始。
