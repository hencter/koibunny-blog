个人知识库的常见死法不是「没内容」，而是**没人做交叉链接和清理**。
内容会自然堆积，但让 29 篇笔记互相连成一张图，是一件没有人愿意长期干的事。

这正是代理擅长的工作：规则明确、重复度高、每次改动都很小。
[Nova](/projects/nova/) 就是按这个前提设计的——它不是应用，是一套**约定 + 技能 + 目录契约**。

## 两层：内核与运行时适配

最开始的版本把「代理专属的路径」写进了正文笔记里，后果是换个运行时就要改一批笔记。
现在拆成两层：

| 层 | 内容 | 换运行时时 |
| --- | --- | --- |
| 内核 | 目录契约、`AGENTS.md` 规则、`concepts/` `patterns/` `templates/` | 不动 |
| 适配 | 技能目录位置、运行配置文件名 | 整体替换 |

落到具体目录上，同一份库有两种形态：

| | Codex 版 | OpenCode 版 |
| --- | --- | --- |
| 技能目录 | `.agents/skills/` | `skills/` |
| 运行配置 | `.codex/` | `opencode.jsonc` |
| 技能数量 | 4 | 4 |

`tools/` 目录里那 8 篇笔记（Codex、OpenCode、Cursor、Copilot、Aider……）
回答的正是这个问题：同一个知识库，不同的代理运行时，规则要不要变。
答案通常是**内核不变、适配层换掉**，而且这个结论值得写下来——
否则每次换工具都会重新讨论一遍要不要重构整个库。

一个具体例子：`auto-commit` 技能只依赖 git 命令，所以两个运行时的技能内容完全一致；
真正不同的只是它住在哪个目录、以及谁在什么时机自动加载它。

## 约束一：初始化必须有两个触发器

别人克隆走的库不能带着原主人的身份继续跑。初始化判据是：

1. `log.md` 里没有任何历史条目 —— 全新仓库，从没跑过；
2. `user-config.md` 里 `owner_name` 仍是 `"未设置"` —— 库是旧的，但身份没配。

```
任一条件成立 → 强制进入初始化问答
```

只留一个都不够：

- 只判断日志，会漏掉「把整个目录复制给别人」这种克隆方式——日志是有效的，人换了；
- 只判断身份，会漏掉「全新仓库」——身份字段存在但从来没被用过，而库还是空的。

这两个失败模式我各遇到过一次，第二次之后才把两个判据都写进规则。

## 约束二：确定性的事不交给模型

技能里凡是「步骤固定、结果应当唯一」的操作，全部写成脚本：

- 图片提取要绕过某个文件名后缀的盲点——写 shell 脚本，不写提示词；
- 提交信息要包含改了哪些文件——从 `git status` 生成，不让模型概括；
- 健康检查要输出固定格式的问题列表——校验脚本决定格式。

理由不是不信任模型，而是**成本**：交给模型做，你就有了「每次结果不太一样」
和「改一次输出格式要把流程重跑一遍」这两笔开销。
判断类的活（这篇笔记该链到哪、这段内容算不算新知识）才交给模型。

## 约束三：持久化就是提交

代理每完成一轮维护就提交一次。这条规则的收益不在「有版本控制」：

- **记忆落在 git 里**，而不是某个会话的上下文里。换代理、换机器、隔半年回来，读提交历史就能接上；
- **回滚粒度是一篇笔记**，而不是整库。

成本也很实在：

- 提交频率高，需要防住密钥与私人内容进历史；
- `user-config.md` 这类文件只能靠 `.gitignore` 挡——**过滤晚一步，密钥就已经在历史里了**。

{{< callout type="warn" title="这条约束最容易做反" >}}
「代理每轮都提交」听起来很安全，但它的前提是 `.gitignore` 在任何一次提交之前就已经写对。
如果你打算让代理自动提交，先把 ignore 规则写完、`git init`、再让它动手——
顺序错了以后要重写历史，而重写历史意味着已经克隆的人手上留着一份删不掉的副本。
{{< /callout >}}

## 现在还不满意的两处

- **跨库引用没有做**：两个 Nova 库之间没法互链，导致「工作」和「个人」两边各有一份重复笔记。
- **健康检查没有测试**：`nova-kb` 的巡检流程现在靠人工确认结果是否符合预期，
  而它恰恰是最该有回归测试的部分——检查逻辑写错了，代理会安静地告诉你「一切正常」。

补这两件事的顺序我倾向于反过来：先给巡检加测试，再考虑跨库引用。
理由还是那个——**会安静说「正常」的东西，优先级最高。**
