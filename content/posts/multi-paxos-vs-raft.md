「用 Raft」几乎是现代分布式系统的默认答案：可理解性优先，实现路径清晰。我们也是这么起步的。
半年后，我们把共识层换成了 Multi-Paxos。这篇文章记录为什么，以及换完之后我们后悔了什么。

## 起点：为什么一开始选 Raft

理由和所有人一样：Raft 把 Leader 选举、日志复制、安全性拆成三块互不干扰的规则，
每条规则都能单独写测试。对我们这种三人小组来说，**可理解性就是可维护性**。

第一版跑得不错。单集群三副本，写入 p99 在 12 ms 左右，成员变更一个月一次。

## 转折点：成员变更的频率变了

真正的变化来自产品：我们要支持按租户扩缩副本，成员变更从「一个月一次」变成「一天几十次」。
Raft 的单步成员变更（一次加或减一个节点）在这个频率下暴露了两个问题：

1. **每次变更都要重新选举或至少阻塞提交**，租户越多，尾延迟越难看。
2. **连续变更之间存在窗口**，中间态如果掉线，恢复逻辑要处理「日志里的配置新旧混合」。

我们试过联合共识（joint consensus）做批量变更，正确性没问题，但实现复杂度涨得比收益快。
一个季度里，成员变更相关的 bug 占了所有 P0 的 60%。

{{< callout type="info" title="数字不会说谎" >}}
统计口径：变更频次从 1 次/月升到 40 次/天之后，成员变更路径的 P0 故障从 0 变成
平均每季度 3.6 次，占同期 P0 总数的 60%。这不是实现质量问题，是路径被放到了它没被设计的位置。
{{< /callout >}}

## Multi-Paxos 给出的东西

Multi-Paxos 的核心差别是：**它把「选出一个稳定的 Leader」和「决定一条日志的位置」解耦了**。
一旦 Leader 稳定，后续的日志条目可以各自独立地在一次往返内被决定，
不需要为每条条目重新确认配置。

对我们来说，收益集中在三点：

- **成员变更可以不阻塞提交**。新配置作为普通日志条目复制，生效点是确定的。
- **乱序提交**。落后的副本不会拖慢已经达成的多数派。
- **没有「配置变更窗口」**。任何时刻都只有一份有效的配置，只是它可能在日志的某个位置。

代价同样清楚：**乱序意味着读路径必须更小心**。Raft 里「已提交的前缀」是天然连续的，
Multi-Paxos 里不是。我们必须维护每个 slot 的依赖关系，才能回答「这个读能不能看到那条写」。

## 架构对比

```text
Raft                                  Multi-Paxos
────                                  ────────────
Client ──► Leader ──► log[0..n]       Client ──► Leader
                    (严格连续)                     │
                                                   ├──► slot 12  ✓ 多数派
                                                   ├──► slot 14  ✓ 多数派（乱序先达成）
                                                   └──► slot 13  ⏳ 落后副本
                      提交点 = 最后一个                  提交点 = 每个 slot 独立
                      连续多数派位置
```

关键数据结构从「一个 commitIndex」变成「一张 slot 状态表」：

```go
type SlotState struct {
    Index     uint64
    Phase     Phase // Idle, Accepted, Committed, Applied
    Accepted  map[NodeID]Ballot
    Value     []byte
    DependsOn []uint64
}

// 读路径必须显式等待依赖，不能假设 Index 之前的都已提交。
func (r *Replica) ReadAt(index uint64) ([]byte, error) {
    if err := r.waitDependencies(index); err != nil {
        return nil, err
    }
    return r.stateMachine.Get(index)
}
```

## 实测数据

同一套硬件、同一个压力模型，只替换共识层：

| 指标 | Raft | Multi-Paxos | 变化 |
| --- | --- | --- | --- |
| 写入 p50 | 11.4 ms | 9.8 ms | −14% |
| 写入 p99 | 34.2 ms | 21.7 ms | −37% |
| 写入 p99.9 | 128 ms | 46 ms | −64% |
| 成员变更耗时 | 2.1 s | 0.34 s | −84% |
| 成员变更期写入成功率 | 92.6% | 99.97% | +7.4pp |
| 代码行数 | 6.1k | 9.4k | +54% |

最后一行是重点。**我们用 54% 的代码量换来了尾延迟的显著改善**。
如果成员变更频率没有涨，这笔交易是亏的。

## 我们后悔的地方

Multi-Paxos 的实现难度被严重低估了。具体来说：

- **调试复杂度非线性上升**。乱序意味着一次不一致可能是三个 slot 交互的结果，
  而 Raft 的 bug 通常能定位到一条日志。
- **测试成本更高**。我们最终靠一个确定性模拟器（可注入时钟、网络分区、崩溃点）才敢上线，
  这个模拟器本身花了两个月。
- **招人更难**。懂 Raft 的工程师遍地都是，能从零写对 Multi-Paxos 的很少。

{{< callout type="danger" title="别为了简历选型" >}}
如果你的成员变更频率低于每天 1 次，不要选 Multi-Paxos。Raft 在那种负载下的表现足够好，
而 Multi-Paxos 多出来的 3.3k 行代码会是你未来三年里最不想维护的东西。
{{< /callout >}}

## 什么时候值得换

我给出一条可操作的判断标准：**成员变更占总写入操作的比例超过 5%**，才值得考虑。
低于这个数，Raft 的简单性收益更大。

我们当时的比例是 11%，所以换了。现在回头看，这个决定是对的，但赢在我们**同时**投了
两个月的测试基建——没有它，Multi-Paxos 的复杂度会直接吃掉所有收益。
